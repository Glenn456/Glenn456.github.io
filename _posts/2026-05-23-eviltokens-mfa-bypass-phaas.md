## The Attack That Does Not Need Your Password

In February 2026, a new Phishing-as-a-Service (PhaaS) platform called EvilTokens appeared on underground Telegram channels. Within five weeks, it had compromised more than 340 Microsoft 365 organisations across five countries including the United States, Canada, Australia, New Zealand, and Germany.

What made EvilTokens notable was not its scale. It was its method.

EvilTokens does not steal passwords. It does not send users to fake login pages. It does not try to intercept MFA codes. Instead, it routes victims through Microsoft's own legitimate authentication infrastructure, gets them to complete their real MFA challenge, and walks away with a valid OAuth token that grants persistent access to their mailbox, OneDrive, Teams, and calendar.

The user sees a real Microsoft page. The MFA prompt is genuine. Everything looks correct. And yet the attacker now has access that survives password resets and persists for weeks or months.

This is a fundamental shift in how identity attacks work.

---

## Understanding the Attack: OAuth Device Code Flow

To understand EvilTokens, you first need to understand the OAuth 2.0 Device Authorization Grant, also known as device code flow.

Device code flow was designed for devices that cannot display a browser or handle complex input, think smart TVs, CLI tools, IoT devices. The flow works like this:

1. The device requests a short code from the authentication server.
2. The user is told to go to `microsoft.com/devicelogin` and enter the code.
3. The user authenticates normally on their phone or computer, completing MFA.
4. The device receives an OAuth access token and refresh token, and is now authenticated.

This is a legitimate flow. Microsoft built it. Enterprises use it every day.

EvilTokens weaponises it.

## How EvilTokens Executes the Attack

**Step 1: The lure**

The victim receives a phishing email crafted using AI to match their role and organisation. Common themes include shared document notifications, SharePoint access requests, password expiration alerts, and DocuSign or Adobe signature requests. The email does not link to a fake login page. It contains a code and instructions.

**Step 2: The device code is generated by the attacker**

Before sending the email, the attacker's platform generates a real device code by calling Microsoft's OAuth endpoint. This produces a legitimate short code. EvilTokens automates re-generation so the 15-minute window never effectively closes.

**Step 3: The victim completes authentication on Microsoft's real site**

The victim goes to `microsoft.com/devicelogin`, a real Microsoft URL, and enters the code. They are prompted to sign in normally and complete their MFA challenge using their real authenticator app. Everything is genuine. Microsoft issues the token.

**Step 4: The token goes to the attacker**

Because the attacker initiated the device code request, the resulting OAuth access token and refresh token are issued to their session. The attacker now has persistent access to the victim's Microsoft 365 account.

The victim walks away believing they confirmed a routine sign-in.

---

## Why This Breaks Everything Defenders Rely On

**MFA is useless here.** The user completes a legitimate MFA challenge on a real Microsoft page. MFA is not bypassed, it is completed correctly on the attacker's behalf.

**Password resets do not help.** Refresh tokens remain valid until explicitly revoked. An organisation that detects the compromise and resets the affected password may believe the incident is contained while the attacker retains full access.

**Traditional SIEM rules do not fire.** Because the token is generated through a legitimate authentication flow, the sign-in event in Azure AD logs looks completely normal. Standard alert rules built around credential theft will miss this entirely.

**Refresh tokens survive for weeks.** In many organisations, refresh tokens are valid for 90 days or more under default tenant policies.

---

## What to Look for in Your Logs

**Azure AD / Entra ID Sign-In Logs**

Look for sign-in events using the device code flow where the associated application name is unfamiliar or generic. The field to check is `authenticationProtocol` or look for `deviceCode` in the grant type. Legitimate device code usage in your environment should be limited to specific known applications.

**Impossible travel with token re-use**

If a refresh token issued in Nairobi is then used from an IP in Eastern Europe, that is a strong indicator of token theft. Monitor for geographic anomalies in token refresh events, not just initial sign-ins.

**Suspicious OAuth app consents**

Audit your Entra ID tenant regularly for OAuth app consents, particularly those granted to apps with names mimicking legitimate Microsoft products that are not actually Microsoft-registered apps.

**High mailbox activity immediately after authentication**

After gaining access, operators often immediately harvest the mailbox. Unusually high email read activity in the first hour after authentication is a behavioural indicator worth alerting on.

---

## Immediate Defensive Actions

**Disable device code flow if you do not need it.** For most organisations, the device code grant type is not required. Restrict it via Conditional Access policies in Entra ID. This eliminates the primary attack mechanism entirely.

Navigate to: Azure Portal > Entra ID > Security > Conditional Access, then create a policy blocking the device code grant for all users except service accounts that genuinely require it.

**Audit active refresh tokens.** Run a review of long-lived refresh tokens in your tenant. Any token older than 30 days for a non-service account should be evaluated and revoked where appropriate.

**Set token lifetime policies.** Configure Entra ID token lifetime policies to enforce shorter refresh token windows for user accounts. A 24-hour refresh token is significantly harder to exploit than a 90-day one.

**Train users on uninitiated authentication prompts.** If a user receives an email asking them to enter a device code at Microsoft's site without having requested access to anything, that is a red flag. One phone call to IT before complying stops this attack entirely.

## The Commoditisation of MFA Bypass

EvilTokens is not alone. The FBI issued a warning in April 2026 about Kali365, another PhaaS platform on Telegram using the same device code technique. It provides AI-generated phishing lures, automated campaign templates, and real-time dashboards for a subscription fee.

What began as a state-sponsored Russian intelligence technique in 2024 is now a commercial service available to low-skill attackers with a Telegram account and a credit card.

MFA was always a strong control. It was never a complete one. The assumption that completing an MFA challenge confirms legitimate access is now broken at the protocol level.

---

## Key Takeaways

- EvilTokens bypasses MFA by routing victims through Microsoft's real authentication flow. The user completing a genuine MFA challenge is the attack itself.
- Refresh tokens issued through this technique survive password resets and remain valid for weeks under default tenant policies.
- Standard SIEM rules built around credential theft will miss this entirely. Detection requires monitoring token grant types and post-authentication behaviour.
- Disabling the device code grant type for user accounts via Conditional Access eliminates the primary attack vector.
- MFA bypass has been fully commoditised. Multiple PhaaS platforms now offer this capability to unskilled attackers for a monthly fee.

Completing your MFA challenge is no longer proof that you are the one logging in. Defenders need to update their detection model accordingly.
